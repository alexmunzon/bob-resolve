# PR 10 notes: the frozen matcher on the held-out two-agency world

Branch `pr-10-commons`. Code: `engine/src/bob_resolve/load/commons.py` (pin, generation, hashes),
`truth/multi.py` (answer key), `run/__init__.py` (two-agency loading, `held_out` scorecard
block), `cli.py` (`--world`). Tests: `tests/unit/test_commons_world.py`,
`tests/e2e/test_multi_a_b.py`, `tests/e2e/test_snapshot.py::test_phase_1_numbers_unchanged`.

**The matcher is frozen.** No weight, cutoff, guard rail, blocking key, nickname table, or
normalizer changed. Every number below is held-out: generated by agency-data-commons v0.2.0,
never used to tune the matcher. Measured on synthetic data, as of 2026-10-01.

## Decisions

1. **The pin (TEMPORARY).** `pyproject.toml` has
   `agency-data-commons @ git+file:///Users/alexmunzon/Data%20intake/agency-data-commons@v0.2.0`.
   The space in "Data intake" is written `%20` (URL encoding), and uv accepts that form. `uv add` writes the URL into
   `[tool.uv.sources]` instead; it was moved back inline so the dependency line itself states
   the tag, which needs `[tool.hatch.metadata] allow-direct-references = true`. `uv.lock` pins
   commit `a9a670fbd9ebced6f2201177d20716fb9944a4c0` (tag v0.2.0). When the commons GitHub repo
   exists this becomes `git+https://github.com/alexmunzon/agency-data-commons@v0.2.0` (same
   tag). Until then the build only works on this Mac, and CI elsewhere cannot resolve it.
2. **Generate, do not copy.** Agency B and the truth files are generated by commons'
   `generate_multi(seed=42, agency_a=False)` into git-ignored `fixtures/generated/multi-a-b/`
   (about 3 seconds, on first use), then checked against `EXPECTED_SHA256`: the hashes of the
   files commons commits at v0.2.0. Generated output was diffed against all 22 committed commons
   files: byte-identical. A mismatch stops the run. This keeps about 1 MB of data out of the repo
   and proves the pin and the committed fixtures agree.
3. **Agency A is the frozen snapshot.** Its `clients.csv` hash equals commons' seed 42 reference
   hash, so it is the same agency A commons' truth files describe.
4. **The world** is four sources: A clients and A enrollment (snapshot), B `canonical/clients.csv`
   and B `drop/enrollment_export.csv`. B's CRM side is its canonical table, the same choice as A's
   `canonical-defected/clients.csv`. B enrollment rows get ids `enrollment:B-<row>` so they never
   collide with A's `enrollment:<row>`.
5. **Answer key.** People are commons' `cluster_truth.json` (3,252 people, 3,600 client ids).
   Each enrollment row joins the person whose client owns its policy number in that agency's
   policies file, as in the snapshot key; rows that do not resolve are reported (9, all agency A,
   the same rows phase 1 reports). That gives 4,969 true record pairs. `pair_truth.jsonl` (320
   client pairs) and `must_not_merge.jsonl` (164) are kept as given.
6. **Two recall numbers.** The SPEC target counts all 4,969 record pairs, most of them easy
   CRM-to-enrollment pairs inside one agency. The scorecard also reports recall on commons' 320
   client pairs (`held_out.commons_pairs`), the cross-agency question this world exists to ask.
   It is tested as a target too, and it misses.
7. **Must-not-merge is checked per person, not per record.** A pair counts as merged when one
   golden person holds any record of each of the two true people. Checking only the two client
   records hid 4 look-alike merges that happened through enrollment rows.
8. **Misses are strict xfail**, with the measured numbers in the reason, never weakened. A fix
   that makes one pass fails the suite until the marker is removed.

## Target tests
- Pass in both modes: blocking recall at least 0.98, precision at least 0.99, recall after
  review at least 0.90 (all record pairs).
- **xfail in both modes:** zero must-not-merge merges; recall at least 0.90 on the 320 commons pairs.

## Failure patterns (for the fix PR; not tuned here)
1. **Opposite-sex twins one letter apart auto-merge.** Andrew and Andrea, Robert and Roberta,
   Brian and Briana, Christian and Christina: one edit, five or more letters, not in
   `FORMAL_GIVEN_NAMES`, so `first_name_typo` calls it a typo and GR-005 stays silent. Same
   household, phone, DOB. Example: `crm:B-C-00582` Andrew Holland and `crm:B-C-01533` Andrea
   Holland (both modes; MBI blank on both).
2. **A move looks like ambiguity.** The mover's records disagree on ZIP and phone, so GR-004
   marks their own identity key ambiguous and the pair goes to review as "unsure", even with the
   same MBI. Example: `crm:C-00240` and `crm:B-C-00154` Joshua Carter, MBI equal, gray GR-004.
3. **Same name and DOB leak through enrollment rows (no shared ids).** Enrollment rows carry no
   ZIP or contact, so GR-007's uniqueness check finds nothing that conflicts and auto-matches.
   Example: `enrollment:1127` (A, client `C-01229`) and `enrollment:B-228` (B, `B-C-00256`),
   Brian Hawkins 1957-03-17, ZIPs 24961 and 25954.

## Risks
- The local `file://` pin breaks on any other machine and in hosted CI until the GitHub URL.
- `fixtures/generated/` is rebuilt when missing; a different faker or openpyxl would change the
  bytes, and the hash check then stops the run (by design).
- The full-key recall (0.93 to 0.96) flatters the matcher; quote the 320-pair number next to it.
